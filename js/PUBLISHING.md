# Publishing onnxoptimizer to npm

The npm package ships the same optimizer as the PyPI package, compiled to
WebAssembly. It is versioned from `VERSION_NUMBER` at the repository root, so
`onnxoptimizer@0.4.2` on npm and `onnxoptimizer==0.4.2` on PyPI are built from
the same source.

## What ships

| Path | Contents |
| --- | --- |
| `dist/onnxoptimizer.mjs` | Emscripten loader, generated by `scripts/build_wasm.sh` |
| `dist/onnxoptimizer.wasm` | the optimizer, ONNX and protobuf-lite (~1 MB) |
| `src/index.mjs` | the JavaScript API |
| `src/index.d.ts` | its TypeScript types |

`dist/` is not checked in; the release workflow builds it.

## One-time setup

1. Claim the `onnxoptimizer` name on npm with an account that maintains it.
   The registry has no such package yet, so the **first publish has to come
   from a maintainer's machine** — npm cannot mint a provenance token for a
   package it does not know about, and a trusted publisher cannot be
   configured before the package exists.
2. Create an automation access token for that account and store it as the
   `NPM_TOKEN` secret of the `release` environment (the same environment the
   PyPI release job uses).
3. After the first release, consider switching to npm's trusted publishing:
   configure `onnxsim/optimizer` and `.github/workflows/npm.yml` as the
   package's trusted publisher on npmjs.com, then drop the `NODE_AUTH_TOKEN`
   line from the publish step. The workflow already requests the `id-token`
   permission that requires.

## Releasing

1. Bump `VERSION_NUMBER`, then sync the package version:

   ```bash
   cd js && node scripts/prepack.mjs --write
   ```

   CI fails the build when the two disagree.

2. Merge, then push a `vX.Y.Z` tag. The `Build and Publish the npm package`
   workflow builds the module, runs the tests, packs the tarball and publishes
   it with `npm publish --provenance --access public`. The publish job is
   gated on the `release` environment, so it waits for whatever approval that
   environment requires.

Every push to `main` and every pull request touching the optimizer, the build
or `js/` runs the same build and test steps without publishing, so a broken
WebAssembly build shows up before a release.

## Publishing by hand

Needed for the first release, and useful when debugging the packaging:

```bash
git submodule update --init --recursive
# Requires an activated emsdk (emcmake on PATH) and a host protoc matching the
# protobuf version onnx pins.
./js/scripts/build_wasm.sh
cd js
npm test
npm publish --access public   # add --dry-run first
```

`npm publish` runs `scripts/prepack.mjs`, which refuses to pack when
`package.json` and `VERSION_NUMBER` disagree or when `dist/` is missing.
